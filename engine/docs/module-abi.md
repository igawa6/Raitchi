# Provisional native module contract

`native/module_abi.h` and `native/module_abi.c` demonstrate the metadata constraints identified in the [runtime audit](runtime-audit.md) and [private-input audit](game-input-audit.md). They are standalone C11 code with no allocation or library dependencies. This is an experimental contract, not the final ABI, an upstream change, a game loader, or an extracted shared runtime.

The runtime supplies a `ModuleAbiProfile` with independent expectations. A loaded library supplies a `ModuleAbiDescriptor`. `module_abi_validate()` compares them without calling a guest function, allocating memory, mapping modules, or modifying either input. It returns a status plus optional module/function indices; the indices are zero-based and use explicit sentinels when no index applies.

`module_abi_validate_profile()` independently checks those expected identity,
module metadata, order, ranges and declared table capacities before layout
selection or `dlopen`. This lets the execution gate reject a malformed local
profile without consuming the session or running native constructors. Actual
descriptor/address/function-table validation still happens after native loading.

The contract checks:

- Exact structure sizes and provisional version 1. Unknown versions, enlarged structures and nonzero reserved fields are rejected; forward compatibility is deliberately undefined.
- Android arm64 LP64 target identity and an explicit CPU layout identity, size and alignment. Legacy `MODULE_ABI_CPU_A64_PREFIX_1024` and `MODULE_ABI_CPU_A64_CACHE_66560` remain distinct, incompatible identities. New `MODULE_ABI_CPU_A64_SHARED_66560` (identity3) describes the [implemented common CPU](shared-aot-execution.md), including the explicitly reserved `excl_hi` at336 and cache at1024; it is not interchangeable with legacy identity2 despite equal size. All specify16-byte alignment; the shared register prefix has `sp=256`, `pc=264`, `nzcv=272`, `fpcr=320`, `fpsr=328`, and vectors at512. Only the shared execution gate requires identity3; the standalone validator also retains legacy profiles for reference tests.
- Exact guest shift and actual half-open guest window. Module bases are canonical addresses; actual bases are obtained by checked subtraction of the shift. Address tables contain actual shifted guest addresses.
- Exactly two modules in main/SDK order, or four in main/SDK/subsdk0/subsdk1 order, as selected by the expected profile. Each module must match its expected full 32-byte NSO build ID, whole-file SHA-256 declaration, canonical base, mapped size, text offset/size and generated function count. Blank IDs/hashes are rejected; trailing zero bytes are retained and compared.
- Nonempty module/text ranges, no shift underflow or endpoint overflow, containment in the expected window and module image, and no pairwise module overlap. Adjacent half-open ranges are allowed. Layout values must equal the profile; actual page-size policy will be supplied by the integration.
- Matching nonzero address/function counts, readable table pointers supplied by the caller, strictly increasing unique instruction-aligned guest addresses within each module’s text, and nonnull host function entries. Impossible counts exceeding text instruction capacity or pointer-index capacity are rejected. Nonnull host functions may be shared between different guest addresses.

The expected profile is a runtime-owned trust input. It must come from a separately validated build/module manifest, including the expected generated function count; copying a loaded descriptor into the expected profile would defeat the comparison. The validator checks declarations against expectations. It does **not** hash NSO files, verify that mapped memory contains those files, inspect executable permissions, prove the declared CPU layout matches a compiled `Cpu`, or establish function semantics. Real runtime integration needs compile-time assertions against its actual `Cpu` and generated-code settings, plus file verification and import/export checks.

The intended call order is: verify an independent sidecar manifest and files; `dlopen` the title library; obtain its metadata descriptor; validate it against runtime-owned expectations; only on `MODULE_ABI_OK` initialize guest modules or enter a guest function. Validation is therefore **after `dlopen`, before guest entry**. The [native loader](module-loader.md) now implements the descriptor **data object** `recomp_module_descriptor_v1`; the [shared execution gate](shared-aot-execution.md) binds validated synthetic producers to dispatch. Serialized sidecar/file verification and real-game integration remain pending. `dlopen` can run library constructors, so this validator does not make an untrusted library safe to load.

All pointer targets must already be readable arrays of the declared sizes and must stay immutable for validation and subsequent use. C cannot establish those extents from a pointer. The descriptor is an in-process native C representation, not a serialized wire/file format; it does not protect against malicious pointers or concurrent mutation. No function pointer is invoked during validation. Fresh Android processes per title/session remain required by the platform plan.

Run `python3 tools/check_module_abi.py` for offline verification. The utility builds only the validator and synthetic tests into ignored `build/module-abi/`, executes optimized and ASan/UBSan host variants, and compiles both translation units with NDK r27c for Android arm64/API 30. It also checks the arm64 validator object for undefined symbols. Host Clang and the offline NDK are required; `--clang` and `--ndk` select other installed paths.

Verified on 2026-10-25:123 synthetic positive/negative checks pass in both host variants (80 descriptor checks and43 independent-profile checks); Android arm64 compilation and dependency checks pass. Tests cover both module inventories and all three CPU identities, including legacy2/shared3 rejection despite equal sizes, shifted/unshifted profiles, boundary-adjacent mappings, full-ID/hash mismatches, counts/order/size/version/target failures, range overflow and underflow, overlaps, invalid tables and null functions. Synthetic guest callbacks remain uncalled in this standalone validator suite. The test inputs contain no game assets, IDs, hashes or generated game code.

No Android execution or real-game integration was performed for this component. These checks do not establish that two titles load an identical runtime artifact or that either title works through this interface. The shared-runtime acceptance gate remains open.
