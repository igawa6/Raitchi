# nxport CPU and profile audit

Read-only source review, 2026-10-25. Reference: `nxporting/nxport` commit `3a5d23c67f23346a9bca0a03d4e03b01375090c4`, inspected in `work/nxport-audit`. No reference code incorporated, builds performed, or device actions taken. Runtime behavior and performance on Thor remain untested. Source is MIT licensed; incorporation would require preserving its notice.

**Recommendation:** retain the working shared C-AOT runtime while testing a separate native ARM64 execution backend. nxport demonstrates a credible route to avoiding per-title C generation, but its current CPU implementation requires an Android ABI port. Its generic fallback is an attempt to execute unfamiliar games, not evidence of compatibility with every game.

## What it actually executes

nxport maps original NSO code, relocates it, patches selected instructions and SDK entries, and executes the remaining ARM64 instructions directly. Its CPU module explicitly identifies native execution ([cpu/mod.rs:1](https://github.com/nxporting/nxport/blob/3a5d23c67f23346a9bca0a03d4e03b01375090c4/crates/engine/src/cpu/mod.rs#L1)). The `aot.rs` name describes packaging already-patched native bytes into a signed iOS code image, with per-run pointers in a separate literal pool; it does not describe ARM-to-C compilation ([cpu/aot.rs:1](https://github.com/nxporting/nxport/blob/3a5d23c67f23346a9bca0a03d4e03b01375090c4/crates/engine/src/cpu/aot.rs#L1), [187](https://github.com/nxporting/nxport/blob/3a5d23c67f23346a9bca0a03d4e03b01375090c4/crates/engine/src/cpu/aot.rs#L187)). Without image mode, `make_exec` uses RW-to-RX `mprotect` ([148](https://github.com/nxporting/nxport/blob/3a5d23c67f23346a9bca0a03d4e03b01375090c4/crates/engine/src/cpu/aot.rs#L148)).

Our CPU3 backend instead supplies generated functions taking `Cpu *`, with guest registers, TLS values, exclusive state and a dispatch cache stored explicitly ([aot_cpu.h:35](../native/runtime/aot_cpu.h#L35)). Its producer compiles generated C into a game library using `-ffixed-x18` ([build_shared_gamelib.py:340](../tools/build_shared_gamelib.py#L340)). A native backend could avoid this compilation and dispatch overhead, but it needs its own entry/exit contract. Native guest registers cannot simply be passed to existing `HostFn(Cpu *)` implementations: a bridge must materialize and restore the required guest state, stack arguments and results, including nested callbacks.

## SDK imports and title discovery

nxport resolves main imports in this order: its SDK HLE registry, original SDK symbols, null for undefined weak symbols, then a diagnostic fallback for unresolved strong imports ([loader.rs:443](https://github.com/nxporting/nxport/blob/3a5d23c67f23346a9bca0a03d4e03b01375090c4/crates/engine/src/guest/loader.rs#L443)). That fallback logs and returns zero ([hle.rs:94](https://github.com/nxporting/nxport/blob/3a5d23c67f23346a9bca0a03d4e03b01375090c4/crates/engine/src/horizon/hle.rs#L94)); the SDK's unresolved-external fallback also returns zero ([sdk_loader.rs:213](https://github.com/nxporting/nxport/blob/3a5d23c67f23346a9bca0a03d4e03b01375090c4/crates/engine/src/guest/sdk_loader.rs#L213)). Therefore successful loading can conceal missing functionality. Our loader deliberately fails unknown strong imports ([loader.c:221](../ports/shared-android/runtime/loader.c#L221)); preserve that behavior in a native proof.

It also patches SDK **definitions**, so internal SDK calls reach the same HLE providers as game imports. Small functions receive a branch island instead of a 16-byte patch that would overwrite their neighbors ([sdk_loader.rs:46](https://github.com/nxporting/nxport/blob/3a5d23c67f23346a9bca0a03d4e03b01375090c4/crates/engine/src/guest/sdk_loader.rs#L46), [lib.rs:598](https://github.com/nxporting/nxport/blob/3a5d23c67f23346a9bca0a03d4e03b01375090c4/crates/engine/src/lib.rs#L598)). This is a useful design to study when broadening SDK versions; its HLE functions and assembly bridges are not drop-in CPU3 providers.

Profiles identify titles from NPDM and versions from a main Build-ID prefix; profiles add settings, shader-search directories and optional version hooks ([profile/mod.rs:1](https://github.com/nxporting/nxport/blob/3a5d23c67f23346a9bca0a03d4e03b01375090c4/crates/engine/src/profile/mod.rs#L1), [88](https://github.com/nxporting/nxport/blob/3a5d23c67f23346a9bca0a03d4e03b01375090c4/crates/engine/src/profile/mod.rs#L88)). An unknown title receives generic defaults and no version hooks ([183](https://github.com/nxporting/nxport/blob/3a5d23c67f23346a9bca0a03d4e03b01375090c4/crates/engine/src/profile/mod.rs#L183)); known titles with unmatched builds likewise skip the version installer ([lib.rs:944](https://github.com/nxporting/nxport/blob/3a5d23c67f23346a9bca0a03d4e03b01375090c4/crates/engine/src/lib.rs#L944)). This separates generic execution from optional title features effectively. Our current adapter intentionally accepts only two measured baselines, validating CPU3, module order, addresses, capabilities and build identity before selecting once ([title_adapter.c:25](../native/adapters/title_adapter.c#L25), [80](../native/adapters/title_adapter.c#L80)). Discovery can be generalized independently of execution; an unknown title should initially produce an import/ISA/layout report rather than silently run.

## Android and Thor barriers

| Area | Concrete source evidence | Required adaptation |
| --- | --- | --- |
| Host and guest TLS | nxport stores context in fixed Darwin pthread-key slots addressed through `TPIDRRO_EL0` ([tls.rs:35](https://github.com/nxporting/nxport/blob/3a5d23c67f23346a9bca0a03d4e03b01375090c4/crates/engine/src/cpu/tls.rs#L35)). Its HLE return stub writes guest TLS into `TPIDR_EL0` ([loader.rs:531](https://github.com/nxporting/nxport/blob/3a5d23c67f23346a9bca0a03d4e03b01375090c4/crates/engine/src/guest/loader.rs#L531)). Android Bionic uses `TPIDR_EL0` for its own TLS ([Bionic implementation](https://android.googlesource.com/platform/bionic/+/7245c082658182c15d2a423fe770388fec707cbc/libc/private/__get_tls.h)). | Replace the Darwin slot mechanism and rewrite guest TLS reads to an explicitly managed per-thread guest context. Keep Bionic TLS valid across host calls, signals, thread startup and callbacks. Copying the current return stub would corrupt the host TLS contract. |
| x18 | nxport rewrites x18 accesses into islands because some Apple environments do not preserve it ([trampoline.rs:1](https://github.com/nxporting/nxport/blob/3a5d23c67f23346a9bca0a03d4e03b01375090c4/crates/engine/src/cpu/trampoline.rs#L1)). Android reserves x18 for ShadowCallStack ([NDK ABI](https://developer.android.com/ndk/guides/abis#arm64-v8a)). | Always preserve Android's actual x18 and virtualize the guest value. The macOS “run x18 unchanged” option is unsuitable. Replace Darwin TLS loads inside every generated stub. Check indirect jumps, SIMD operands, flags and all other live registers. nxport rejects detected unrenamed x18 operands, which is a good policy ([629](https://github.com/nxporting/nxport/blob/3a5d23c67f23346a9bca0a03d4e03b01375090c4/crates/engine/src/cpu/trampoline.rs#L629)). |
| Exclusive atomics | nxport recognizes short load/store-exclusive sequences touching x18 and emits a combined stub to avoid inserting memory stores inside the exclusive window ([229](https://github.com/nxporting/nxport/blob/3a5d23c67f23346a9bca0a03d4e03b01375090c4/crates/engine/src/cpu/trampoline.rs#L229), [955](https://github.com/nxporting/nxport/blob/3a5d23c67f23346a9bca0a03d4e03b01375090c4/crates/engine/src/cpu/trampoline.rs#L955)). It separately strengthens plain exclusive loads to acquire forms ([exclusive_rewrite.rs:1](https://github.com/nxporting/nxport/blob/3a5d23c67f23346a9bca0a03d4e03b01375090c4/crates/engine/src/cpu/exclusive_rewrite.rs#L1)). | Validate the full sequence decoder and register liveness on real inputs; its search is bounded to the next 15 instructions. Test contention, retries, pair exclusives and x18-dependent addresses on Thor. Native execution can execute pair-exclusive instructions without our pending C-AOT 128-bit helper, but does not automatically establish correct rewriting or host fault recovery. The Apple ordering workaround is source-reported evidence, not a measured Thor requirement. |
| Address space and branch reach | Main/SDK and islands share a reservation; modules use a fixed 32 MiB gap and 16 MiB SDK slot ([loader.rs:9](https://github.com/nxporting/nxport/blob/3a5d23c67f23346a9bca0a03d4e03b01375090c4/crates/engine/src/guest/loader.rs#L9), [119](https://github.com/nxporting/nxport/blob/3a5d23c67f23346a9bca0a03d4e03b01375090c4/crates/engine/src/guest/loader.rs#L119)). TLS islands must fit direct-branch reach and currently use Mach allocation ([tpidr_rewrite.rs:22](https://github.com/nxporting/nxport/blob/3a5d23c67f23346a9bca0a03d4e03b01375090c4/crates/engine/src/cpu/tpidr_rewrite.rs#L22), [80](https://github.com/nxporting/nxport/blob/3a5d23c67f23346a9bca0a03d4e03b01375090c4/crates/engine/src/cpu/tpidr_rewrite.rs#L80)). | Build a Linux reservation/island allocator that never replaces foreign mappings, validates actual image sizes and branch distances, and handles zygote address collisions. Our existing verified session-layout/reservation mechanism is a useful foundation; native relocation policy need not copy the C-AOT fixed-address policy. |
| Host pages and platform glue | Thor was inventoried with **4096-byte pages** ([thor-inventory.md](thor-inventory.md)). nxport hardcodes 16 KiB executable-page rounding ([aot.rs:29](https://github.com/nxporting/nxport/blob/3a5d23c67f23346a9bca0a03d4e03b01375090c4/crates/engine/src/cpu/aot.rs#L29)) and uses Darwin icache APIs ([exclusive_rewrite.rs:17](https://github.com/nxporting/nxport/blob/3a5d23c67f23346a9bca0a03d4e03b01375090c4/crates/engine/src/cpu/exclusive_rewrite.rs#L17)). Its crash handler uses Darwin `ucontext` members ([crash_handler.rs:325](https://github.com/nxporting/nxport/blob/3a5d23c67f23346a9bca0a03d4e03b01375090c4/crates/engine/src/cpu/crash_handler.rs#L325)). | Query host page size and preserve distinct guest-page semantics; 16 KiB protection changes on a 4 KiB host may affect neighboring subranges. Replace Mach allocation, cache flushes and signal-context code. Android also supports 16 KiB hosts, so a permanent 4096 assumption is unsuitable ([Android page-size guidance](https://developer.android.com/guide/practices/page-sizes)). |

Extra NSO module loading also rewrites SVC, `TPIDR_EL0` and guest `TPIDRRO_EL0` reads into service/context stubs ([module_loader.rs:1](https://github.com/nxporting/nxport/blob/3a5d23c67f23346a9bca0a03d4e03b01375090c4/crates/engine/src/guest/module_loader.rs#L1)). These are part of the native execution boundary, not optional performance patches. The reviewed source's Apple dependencies and README explicitly limit current support to Apple Silicon; no Android readiness is established by this audit.

## Smallest useful proof

1. Create an isolated Android native-execution micro-harness, without game assets, GPU or launcher changes. Map synthetic A64 text RW, patch it, flush caches, then make it RX. Exercise guest TLS and x18 across repeated native-to-host-to-native calls, a host callback, two pthreads, scheduling and a signal while verifying Bionic TLS and host x18 remain intact.
2. Add contended exclusive loops, 128-bit pairs, x18 operands, indirect branches and live SIMD/flags checks. Require exact output, bounded retries and rejection of unsupported instructions; compare with a reference result. This tests the hard Android boundary before a game hides failures in thousands of unrelated calls.
3. Only after that passes, execute one independently audited original LAS CPU function through a new backend bridge while retaining the existing shared services/NVN path. Then attempt SDK startup with unresolved strong imports fatal. Compare game state and CPU/power at equal frame rate, resolution, driver and scene before deciding whether to replace C-AOT.

These steps establish a CPU alternative. They do not by themselves fix GPU correctness, remove shader compilation, or make unprofiled titles supported.
