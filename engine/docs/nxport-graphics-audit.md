# nxport graphics and Android feasibility

Audited source: `nxporting/nxport` at `3a5d23c67f23346a9bca0a03d4e03b01375090c4`. This was a bounded source review: no builds, game imports, device runs or reference edits. Android/Thor behavior is unverified. The practical opportunity is a translator comparison and selected interface/cache ideas; adopting the complete engine would require a substantial Android/Vulkan port.

## Generic interface, concrete Metal implementation

There is a real `gpu::Backend: Send + Sync` interface: shader registration, command-list submission, presentation, serial/fence waits, and CPU/GPU memory-coherence callbacks. NVN queue submission and presentation use this interface. That is a useful separation to study alongside our existing NVN/Vulkan boundary. See [gpu/mod.rs:25](https://github.com/nxporting/nxport/blob/3a5d23c67f23346a9bca0a03d4e03b01375090c4/crates/engine/src/gpu/mod.rs#L25-L60) and [nvn/api.rs:6361](https://github.com/nxporting/nxport/blob/3a5d23c67f23346a9bca0a03d4e03b01375090c4/crates/engine/src/nvn/api.rs#L6361-L6464).

The separation is incomplete. Engine startup unconditionally installs the Metal backend, the engine has unconditional Objective-C/Metal dependencies, and NVN memory release directly invokes `metal::rt_guard::released`. The Metal backend's fault callbacks coordinate several page guards, rather than merely issuing draw calls. Replacing `MTLDevice` with Vulkan handles would leave memory ownership, pool release, fault recovery and synchronization unresolved. See [lib.rs:39](https://github.com/nxporting/nxport/blob/3a5d23c67f23346a9bca0a03d4e03b01375090c4/crates/engine/src/lib.rs#L39-L62), [Cargo.toml:21](https://github.com/nxporting/nxport/blob/3a5d23c67f23346a9bca0a03d4e03b01375090c4/crates/engine/Cargo.toml#L21-L41), [nvn/api.rs:1580](https://github.com/nxporting/nxport/blob/3a5d23c67f23346a9bca0a03d4e03b01375090c4/crates/engine/src/nvn/api.rs#L1580-L1585), and [metal/backend.rs:56](https://github.com/nxporting/nxport/blob/3a5d23c67f23346a9bca0a03d4e03b01375090c4/crates/engine/src/metal/backend.rs#L56-L93).

Its no-copy `MTLBuffer` strategy also differs from our Android storage-buffer mirror. Preserve our current Vulkan resource lifetime and guest-memory contract during any translator experiment. Unknown NVN functions can resolve to logging stubs that return zero, so the generic interface does not establish complete NVN coverage. See [metal/translated.rs:16](https://github.com/nxporting/nxport/blob/3a5d23c67f23346a9bca0a03d4e03b01375090c4/crates/engine/src/metal/translated.rs#L16-L17) and [nvn/api.rs:61](https://github.com/nxporting/nxport/blob/3a5d23c67f23346a9bca0a03d4e03b01375090c4/crates/engine/src/nvn/api.rs#L61-L82).

## Direct SASS translation is a credible isolated candidate

`sass2spv` is a separate Rust crate with serde/serde_json dependencies, derived from the Ryujinx translator. `Target::Spirv` directly generates SPIR-V from the structured intermediate representation; `Target::Msl` is an alternative emitter. There is no mandatory GLSL/shaderc or Metal step for the SPIR-V target. The batch CLI emits `.spv` plus a resource-binding manifest. That manifest identifies constant buffers, storage-buffer source slots/offsets, textures and images. See [sass2spv/Cargo.toml:5](https://github.com/nxporting/nxport/blob/3a5d23c67f23346a9bca0a03d4e03b01375090c4/crates/sass2spv/Cargo.toml#L5-L18), [pipeline.rs:111](https://github.com/nxporting/nxport/blob/3a5d23c67f23346a9bca0a03d4e03b01375090c4/crates/sass2spv/src/pipeline.rs#L111-L158), and [main.rs:37](https://github.com/nxporting/nxport/blob/3a5d23c67f23346a9bca0a03d4e03b01375090c4/crates/sass2spv/src/main.rs#L37-L59).

It is not yet a Vulkan-device capability interface. The accessor fixes storage alignment at 16 bytes, subgroup width at 32, fragment interlock and shader float64 support to true, texture types to 2D, and texture formats to RGBA8. SPIR-V generation adds `Float64` whenever that accessor says it is supported, even before considering whether a particular shader needs it. These assumptions must be replaced with the selected Vulkan device's enabled features and actual NVN draw/texture state before treating its output as an Android input. Its descriptor set/binding convention also differs from our current runtime and needs an explicit adapter. See [accessor.rs:170](https://github.com/nxporting/nxport/blob/3a5d23c67f23346a9bca0a03d4e03b01375090c4/crates/sass2spv/src/accessor.rs#L170-L201), [accessor.rs:229](https://github.com/nxporting/nxport/blob/3a5d23c67f23346a9bca0a03d4e03b01375090c4/crates/sass2spv/src/accessor.rs#L229-L316), and [codegen/mod.rs:416](https://github.com/nxporting/nxport/blob/3a5d23c67f23346a9bca0a03d4e03b01375090c4/crates/sass2spv/src/codegen/mod.rs#L416-L427).

The global-to-storage pass traces guest addresses back to constant-buffer words holding storage-buffer bases. This could provide an independent comparison for our current address/carry problems, but its storage bindings still need our mirror's visibility and writeback semantics. Some instruction handlers only log that an operation is unimplemented, and accessor logging defaults off. Successful translation therefore does not prove complete instruction semantics. See [global_to_storage.rs:1](https://github.com/nxporting/nxport/blob/3a5d23c67f23346a9bca0a03d4e03b01375090c4/crates/sass2spv/src/translation/optimizations/global_to_storage.rs#L1-L2), [unimplemented.rs:5](https://github.com/nxporting/nxport/blob/3a5d23c67f23346a9bca0a03d4e03b01375090c4/crates/sass2spv/src/instructions/unimplemented.rs#L5-L64), and [accessor.rs:112](https://github.com/nxporting/nxport/blob/3a5d23c67f23346a9bca0a03d4e03b01375090c4/crates/sass2spv/src/accessor.rs#L112).

## Precompilation reduces work; it does not remove all shader stalls

The cache builder processes only supplied stage dumps or extracted stages, writes failure reports, and compiles MSL into AIR/metallib chunks. Its fingerprint includes translator source, specialization passes and tool flags. Those dependency and coverage records are reusable ideas. The actual artifacts are Metal artifacts. See [shader_cache_build.rs:5](https://github.com/nxporting/nxport/blob/3a5d23c67f23346a9bca0a03d4e03b01375090c4/crates/build/src/shader_cache_build.rs#L5-L21) and [shader_cache_build.rs:635](https://github.com/nxporting/nxport/blob/3a5d23c67f23346a9bca0a03d4e03b01375090c4/crates/build/src/shader_cache_build.rs#L635-L646).

Pipeline archives contain GPU-compiled Metal pipelines; their own implementation explicitly falls back when a GPU/OS compiler or pipeline is absent. Runtime cache misses can synchronously translate and compile MSL. Asynchronous pipeline compilation substitutes skipped draws/pop-in for waiting beyond a per-frame budget. Direct SPIR-V would remove our GLSL compilation step, but Vulkan still needs device-specific pipeline compilation and complete pipeline-state coverage. None of these mechanisms guarantees no shader lag or accurate rendering. See [pipeline_archive.rs:1](https://github.com/nxporting/nxport/blob/3a5d23c67f23346a9bca0a03d4e03b01375090c4/crates/engine/src/metal/pipeline_archive.rs#L1-L5), [shader_cache.rs:527](https://github.com/nxporting/nxport/blob/3a5d23c67f23346a9bca0a03d4e03b01375090c4/crates/engine/src/metal/shader_cache.rs#L527-L534), [shader_cache.rs:602](https://github.com/nxporting/nxport/blob/3a5d23c67f23346a9bca0a03d4e03b01375090c4/crates/engine/src/metal/shader_cache.rs#L602-L643), and [translated.rs:78](https://github.com/nxporting/nxport/blob/3a5d23c67f23346a9bca0a03d4e03b01375090c4/crates/engine/src/metal/translated.rs#L78-L81).

The separate pipeline-list crate has a promising `p2` format using NVN formats and pipeline state rather than Metal pixel formats. Its `p1` format is Metal-specific. A neutral pipeline inventory could feed our existing Vulkan preparation path; `.metallib` and `.metalar` cannot. See [pipelines/lib.rs:1](https://github.com/nxporting/nxport/blob/3a5d23c67f23346a9bca0a03d4e03b01375090c4/crates/pipelines/src/lib.rs#L1-L15).

## Bounded next test

Keep the current Android runtime and title libraries unchanged. In a separate ignored experiment, build only `sass2spv` with pinned dependencies if cached, then translate a tiny synthetic carry/address/storage-buffer fixture and a small private selection of already-captured vertex/fragment/compute stages. Retain control sections, resource manifests and translator diagnostics. First inspect/validate emitted SPIR-V capabilities against the actual enabled Vulkan feature set; the current fixed `Float64` declaration is an immediate acceptance gate. Compare manifest bindings and arithmetic/memory results against the current translator before introducing one opt-in pipeline replay. Do not replace the renderer or assert title compatibility from translation/validation alone. This next test was proposed, not run.
